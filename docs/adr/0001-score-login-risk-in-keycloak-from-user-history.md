# 0001. Login risk is scored inside Keycloak from each user's own history, and the admin's flow decides the response

## Status

Accepted.

## Context

Keycloak ships no risk-based authentication. An admin who wants a second factor only when a sign-in looks unusual can prompt on every login, never prompt, or script fixed rules (a role check, an IP range) that compute no risk at all. The extensions that exist pull in different directions. keycloak-adaptive-authn, an experimental project by a Keycloak developer, is a framework of pluggable risk evaluators that can also consult an AI model. Commercial add-ons sell risk scoring as a separate hosted product. Microsoft Entra ID Protection scores sign-ins against the user's history and global threat intelligence in a paid tier.

Several forces shape the design. A login is the hottest path in an identity server, so a network call per login adds latency and a new outage mode to every sign-in. The result has to be explainable: an admin looking at a blocked user and a SIEM rule both need a named reason, not a bare number. There is no labelled attack data to train a model on, and a pre-trained model would bring a native runtime and a heavy jar. Keycloak's conditional sub-flows already express 'under this condition, require OTP, require WebAuthn, or deny', and admins know that model. Keycloak records failed attempts only when brute force detection is on. When a proxy appends to X-Forwarded-For instead of replacing it, the leftmost entry is whatever the client sent, so a client address is only trustworthy from a header the operator's own proxy always sets. And the extension has to run on any Keycloak 26 deployment, including ones whose caches are not Infinispan.

Five alternatives were considered and rejected. Contributing an evaluator to keycloak-adaptive-authn ties the design, storage and release cadence to an experimental project we do not control, when the goal is to own the whole adaptive flow. Scoring every login with an LLM puts a network call and a cost on every sign-in, adds a failure mode, and lets attacker-controlled text such as the User-Agent reach a prompt. A pre-trained model needs training data we do not have and native libraries, and its reasons are unreadable. Keeping the history in user attributes makes it visible in the admin console and in realm exports, invalidates the user cache on every login, and can be rejected by the declarative user profile. Keeping it in Infinispan caches loses it on restart and does not work where Infinispan is not the cache.

## Decision

Each browser login is scored inside Keycloak against a bounded profile of that user's own past successful logins, and the admin's flow, not the scorer, decides what a risk level triggers. The evaluator turns named reasons (new device, new network, new country, rapid country change, recent failed attempts, unusual hour) into a capped 0 to 100 score and a low, medium or high level with admin-set thresholds. It never challenges the user itself: it hands the level to a 'Condition - risk level' authenticator that gates the admin's own step-up or deny sub-flows. The profile lives in the extension's own table, through a JPA entity and a Liquibase changelog, and is written only when the whole flow succeeds, so a login stopped at step-up teaches it nothing. The client address and country come from headers the operator names, or from Keycloak's resolved address when none is named. Any error during evaluation fails open to low, and says so in the event details and the metrics. A bring-your-own model may be added later as an optional second opinion; the local score is always computed and is always the fallback.

## Consequences

Every Keycloak database that runs the extension gains a table, created at first start and left behind if the extension is removed. Every evaluated login costs one indexed read and, when it succeeds, one write. The provider IDs, the event detail names (risk_score, risk_level, risk_reasons, risk_country) and the table schema become contracts once admins wire flows and SIEM rules against them, so changing any of them needs a migration and a deprecation window.

Learning from each user's own history has blind spots. A user's first logins carry no history signal, so admins choose the score applied while a profile is learning. Users who clear cookies or move between networks are stepped up more often. An attacker who passes step-up once teaches the profile their device. Failing open means a database fault quietly removes step-up until it is fixed, which is why the error outcome is counted and can be alerted on. This version does not include global threat intelligence such as IP reputation, and it does not score logins that run no browser flow, such as the password grant or client credentials.
